## Что я сделал

Структура каталога при каждой сдаче новая, поэтому я не стал писать код под одну
конкретную структуру. Вместо этого я описал структуру **текстовым файлом (spec)**,
а всё остальное делается автоматически: одна программа строит каталог по spec,
а второй скрипт генерирует по тому же spec sh-версию. Для нового варианта задания
достаточно написать новый spec-файл.

| Пункт задания | Как выполнен |
|---|---|
| Программа на C, создающая каталог | `src/fsbuild.c` читает spec и строит дерево системными вызовами |
| sh-скрипт, создающий тот же каталог | `scripts/spec2sh.sh` генерирует его из того же spec |
| Программа, удаляющая каталог | `src/fsremove.c` |
| Подтверждение результата (`ls` / `tree`) | `make demo`, а также автопроверка `make test` |
| Монтирование флешки | раздел «Монтирование флешки» ниже |

```
task.spec ──► fsbuild ──► каталог (C, системные вызовы)
    │
    └──────► spec2sh.sh ──► build.sh ──► тот же каталог (команды оболочки)
```

## Формат spec

Одна команда на строку. Пути отсчитываются от каталога, в котором запущена
программа. Команды выполняются сверху вниз, родительский каталог объявляется
раньше вложенных объектов (как обычный `mkdir` без `-p`).

| Строка в spec | Что создаётся |
|---|---|
| `dir a/b` | каталог |
| `file a/x.txt empty` | пустой файл |
| `file a/x.txt text catts` | файл со строкой (до конца строки, без `\n`) |
| `file a/x.bin random 500` | 500 случайных байт из `/dev/urandom` |
| `file a/x.bin zero 35` | 35 нулевых байт |
| `symlink a/d c` | символьная ссылка `a/d`, в которой записано `c` |
| `hardlink a/e/f.txt a/b/cat.txt` | жёсткая ссылка `a/e/f.txt` на существующий файл |
| `# ...` | комментарий (только с начала строки) |

Пример задания из методички:

```
a/b/cat.txt   ("catts")
 /c/dog.txt   (пустой)
 /d           (ссылка на /c)
 /e/f.txt     (жёсткая ссылка на b/cat.txt)
   /g.bin     (500 байт, случайный)
   /h.bin     (35 байт, заполнен 0)
```

Отступы показывают вложенность: `g.bin` и `h.bin` лежат внутри `a/e/`. Это видно и
по sh-скрипту из методички, где перед ними стоит `cd ../e`.

Соответствующий `structure.spec`:

```
dir      a
dir      a/b
dir      a/c
dir      a/e
symlink  a/d  c
file     a/b/cat.txt  text catts
file     a/c/dog.txt  empty
hardlink a/e/f.txt  a/b/cat.txt
file     a/e/g.bin  random 500
file     a/e/h.bin  zero 35
```

## Как это работает

### 1. `fsbuild` — создание каталога системными вызовами

1. Программа читает spec-файл целиком: `open` → цикл `read` (буфер растёт через
   `realloc`) → `close`.
2. Текст режется на строки, хвостовые пробелы и `\r` убираются (чтобы файл,
   отредактированный в Windows, тоже читался).
3. Для каждой строки определяется команда и вызывается нужная функция:

| Команда | Системные вызовы |
|---|---|
| `dir` | `mkdir(path, S_IRWXU)` |
| `file ... empty/text` | `open(O_WRONLY \| O_CREAT \| O_EXCL, S_IRWXU)`, `write` в цикле, `close` |
| `file ... random` | `open` на `/dev/urandom`, `read` блоками по 4 КБ → `write` в новый файл |
| `file ... zero` | `open` + `ftruncate(fd, N)` — файл дополняется нулями |
| `symlink` | `symlink(target, linkpath)` |
| `hardlink` | `link(existing, linkpath)` |

4. Каждое действие печатается на экран, так что видно, что именно происходит.
   При любой ошибке выводится `вызов(путь): причина`, и программа завершается с
   кодом 1. Ошибки в самом spec сообщаются с номером строки.

Принятые решения:

* Я использовал `O_EXCL` вместе с `O_CREAT`: это гарантирует, что файл создан
  именно мной, а не открыт уже существующий. Поэтому повторный запуск в том же
  каталоге завершается ошибкой, а не затирает данные.
* `write` может записать меньше, чем просили, поэтому запись идёт в цикле (`write_all`).
* Нулевые байты создаются через `ftruncate`: по методичке увеличение файла
  дополняет его нулями, это проще и быстрее, чем писать их вручную.
* Вывод на экран (`printf`) к файловым операциям не относится: ограничение
  методички касается только работы с файлами и каталогами.

### 2. `spec2sh.sh` — генерация sh-скрипта

Это небольшой `awk`-генератор. Он превращает каждую строку spec в обычную команду:

| spec | команда оболочки |
|---|---|
| `dir` | `mkdir` |
| `file ... empty` | `touch` |
| `file ... text` | `printf '%s' '...' > файл` |
| `file ... random N` | `head -c N /dev/urandom > файл` |
| `file ... zero N` | `truncate -s N файл` |
| `symlink` | `ln -s цель ссылка` |
| `hardlink` | `ln существующий ссылка` |

Все имена оборачиваются в одинарные кавычки, в начале ставится `set -e`: скрипт
останавливается на первой ошибке. Для примера из методички получается:

```sh
#!/bin/sh
set -e
mkdir 'a'
mkdir 'a/b'
mkdir 'a/c'
mkdir 'a/e'
ln -s 'c' 'a/d'
printf '%s' 'catts' > 'a/b/cat.txt'
touch 'a/c/dog.txt'
ln 'a/b/cat.txt' 'a/e/f.txt'
head -c 500 /dev/urandom > 'a/e/g.bin'
truncate -s 35 'a/e/h.bin'
```

### 3. `fsremove` — удаление каталога (средний вариант)

Рекурсивный обход: `scandir` (с фильтром, отбрасывающим `.` и `..`) → для
каждой записи либо спуск в подкаталог, либо `unlink` → в конце `rmdir` самого
каталога. Память, выделенную `scandir`, я освобождаю (`free` на каждый элемент и
на массив).

Меры безопасности:

* **Символьные ссылки не разыменовываются.** `scandir` идёт по ссылке на
  каталог, поэтому «наивный» обход мог бы удалить файлы *за пределами* дерева.
  Рекурсия идёт только по записям `DT_DIR`, ссылки (`DT_LNK`) удаляются как файлы.
* Если сам аргумент — символьная ссылка, программа отказывается работать
  (это определяется через `readlink`: на не-ссылке он возвращает `EINVAL`).
* Удаление `/`, `.` и `..` запрещено.
* Если файловая система не сообщила тип записи (`DT_UNKNOWN`), программа пробует
  `unlink`: для каталога он вернёт `EISDIR`, и тогда она идёт внутрь.

### 4. `verify.sh` — автопроверка

Для одного spec-файла скрипт:

1. строит дерево C-программой и sh-скриптом в двух временных каталогах;
2. сравнивает деревья: тип, путь, размер, цель символьных ссылок, счётчик жёстких ссылок;
3. проверяет, что жёсткие ссылки указывают на **один i-node**;
4. сравнивает содержимое всех неслучайных файлов (`cmp`);
5. запускает `fsremove` и проверяет, что каталоги удалены и что файл за
   пределами дерева (на который из дерева ведёт символьная ссылка-«ловушка»)
   остался целым.

Результат `make test`:

```
== structure.spec
  [ OK ]  дерево построено C-программой и sh-скриптом
  [ OK ]  структура совпадает (10 объектов: типы, размеры, цели ссылок, links)
  [ OK ]  [c] a/e/f.txt и a/b/cat.txt — один i-node
  [ OK ]  [sh] a/e/f.txt и a/b/cat.txt — один i-node
  [ OK ]  содержимое совпало у 3 файлов (empty/text/zero)
  [ OK ]  fsremove удалил все каталоги дерева
  [ OK ]  fsremove не пошёл по символьной ссылке за пределы дерева
== PASSED
```

## Запуск

Нужны `gcc`, `make` и обычные утилиты Linux (GNU `find`, `stat`, `awk`). Работа
рассчитана на Linux (Ubuntu); в Windows 11 она запускается через WSL.

```sh
make            # собрать bin/fsbuild и bin/fsremove
```

## Порядок работы с новой структурой

1. Записываю выданную структуру в новый `task.spec` по таблице формата выше.
2. Запускаю `./bin/fsbuild task.spec` и подтверждаю результат командой
   `ls -liR` (или `tree`).
3. Строю ту же структуру скриптом в другом каталоге:
   `sh scripts/spec2sh.sh task.spec > task.sh && sh task.sh`, снова `ls -liR`.
   Сгенерированный `task.sh` — обычный набор команд оболочки, при необходимости
   его можно набрать и вручную.
4. Для среднего варианта запускаю `./bin/fsremove <каталог>` и показываю, что
   каталога больше нет.
5. Для сложного варианта монтирую флешку (см. следующий раздел).

Перед показом я запускаю `sh scripts/verify.sh task.spec`: он сразу сообщает об
опечатке в spec или о расхождении между C-версией и sh-версией.

## Монтирование флешки (сложный вариант)

```sh
lsblk                                  # найти устройство флешки, например sdb1
sudo mkdir -p /mnt/usb                 # каталог для монтирования, если его ещё нет
sudo mount /dev/sdb1 /mnt/usb
mount | grep /mnt/usb                  # убедиться, что смонтировано
ls /mnt/usb
sudo umount /mnt/usb                   # размонтировать после проверки
```

Имя устройства (`sdb1`) у каждого своё, его всегда нужно смотреть в `lsblk`.

## Теоретические пояснения (вопросы и ответы)

**Чем жёсткая ссылка отличается от символьной?**
Жёсткая ссылка — ещё одна запись в каталоге на тот же i-node (у `cat.txt` и
`f.txt` номер общий, счётчик ссылок равен 2). Символьная — отдельный файл, в
котором записан путь к цели.

**Что будет, если удалить `cat.txt`?**
Данные останутся: они доступны через `f.txt`. i-node освобождается, только когда
не осталось ни одной жёсткой ссылки (и файл не открыт ни одним процессом).

**Что будет, если удалить каталог `c`?**
Ссылка `d` станет висячей (dangling): она хранит путь `c`, а такого объекта нет.

**Откуда у `h.bin` нули, если в него ничего не записывалось?**
`ftruncate` увеличил пустой файл до 35 байт, а по методичке недостающая часть
дополняется нулями.

**Зачем `O_EXCL`?**
В паре с `O_CREAT` он делает вызов ошибкой, если файл уже есть. Так создаётся
именно новый файл, а старый не затирается.

**Почему `write` вызывается в цикле?**
Он вправе записать меньше байт, чем просили (например, при нехватке места),
поэтому остаток нужно дописывать.

**Почему `fsremove` не заходит в символьные ссылки?**
`scandir` разыменовывает ссылку на каталог. Обход по ссылке мог бы уйти за
пределы дерева и удалить чужие файлы. Ссылка удаляется как обычный файл (`unlink`).

**Почему сначала удаляется содержимое, а потом каталог?**
`rmdir` удаляет только пустой каталог.

**Зачем `free` после `scandir`?**
Массив и структуры `dirent` выделены через `malloc`, освобождать их должен
разработчик.

## Какие вызовы использованы

Раздел 1.2 методички разрешает для манипуляций с файлами и каталогами только
`getcwd`, `chdir`, `open`, `close`, `read`, `write`, `lseek`, `ftruncate`,
`link`, `symlink`, `readlink`, `unlink`, `mkdir`, `rmdir`, `scandir`.

* `fsbuild`: `mkdir`, `open`, `close`, `read`, `write`, `ftruncate`, `link`, `symlink`.
* `fsremove`: `scandir`, `readlink`, `unlink`, `rmdir`.
* Остальное (`printf`, `malloc`, разбор строк) к файловой системе не относится.
  Тип записи берётся из поля `d_type` структуры `dirent`, которую возвращает
  сам `scandir`, поэтому `stat` не нужен.

## Особенности реализации

* **Цель символьной ссылки отсчитывается от каталога самой ссылки**, а не от
  рабочего каталога. `symlink a/d c` создаёт `a/d -> c`, и `c` ищется внутри
  `a/`. А цель жёсткой ссылки (`link`) — обычный путь от текущего каталога.
* **`echo` добавляет `\n`:** `echo catts > f` даёт 6 байт, а не 5. Для точного
  размера в генераторе используется `printf '%s'`.
* **Висячая ссылка** — это нормально: `symlink` не проверяет, что цель существует
  (см. `lab/dangling` в `examples/second.spec`).
* **Окончания строк:** `.gitattributes` фиксирует LF для `.sh`, `.c`, `.spec` и
  `Makefile`, иначе на Windows `sh`-скрипты ломаются из-за `\r`.

## Ограничения

* Пути в spec не должны содержать пробелов.
* Комментарии `#` допустимы только с начала строки (в `text` решётка — обычный символ).
* `verify.sh` использует GNU `find -printf` и `stat -c`, то есть рассчитан на Linux.
